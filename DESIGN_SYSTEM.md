## Convenção de leitura

Todo ponto relevante deste documento é marcado com um dos três rótulos abaixo, para que fique sempre claro o que é fato, o que é escolha e o que ainda está em aberto:

- **OBSERVADO** — comportamento ou valor comprovado no código atual (com referência a arquivo/linha quando aplicável).
- **DECIDIDO** — escolha que estamos tomando agora para o Design System. Uma decisão `DECIDIDO` pode ir além do que existe hoje no código (ex.: uma prop nova); nesses casos isso é dito explicitamente, para não passar a impressão de que foi "extraída" do código.
- **PENDENTE** — pergunta em aberto que precisa de validação humana antes da implementação correspondente começar.

## 1. Propósito e escopo

O Design System do OrçaFlow consolida o vocabulário visual que já existe na aplicação em componentes reutilizáveis, eliminando duplicações e inconsistências já catalogadas — sem redesenhar o produto. **DECIDIDO:** ele vive co-localizado em `src/design-system/`, dentro do próprio repositório do frontend, sem virar pacote npm nem monorepo neste momento (ver seção 6).

Cobre: os primitivos hoje expressos como classes `@layer components` do Tailwind, os componentes React já extraídos, os padrões hoje duplicados entre páginas (modal, ícone em tile, botão de ícone, badge, campo de busca, campo de formulário, tabela, card de KPI) e os arranjos de página recorrentes. **Não** cobre lógica de domínio, regras de negócio, cópia de marca/marketing ou infraestrutura não-visual — isso permanece na aplicação (seção 11).

## 3. Camadas arquiteturais

**DECIDIDO:** a arquitetura usa **três camadas**, não cinco. A distinção anterior entre `Component` e `Composite` foi eliminada — um componente é um `Component` independentemente de ser feito só de elementos HTML ou de combinar outros componentes.

1. **Primitive** — menor unidade visual indivisível: um elemento HTML + uma regra de estilo, sem sub-componentes, sem lógica.
2. **Component** — qualquer unidade reutilizável com API de props própria, seja composta só de primitivos (ex.: `Badge`) ou de outros `Component`s (ex.: `FormField` = `Label` + controle + `FieldError`; `Modal` = overlay + container + slots).
3. **Pattern** — arranjo de página/fluxo: como `Primitive`s e `Component`s se organizam para resolver uma tarefa (lista com filtro, formulário em página inteira, autenticação). Não é "um componente", é uma composição documentada.

**DECIDIDO:** `Domain-specific` deixa de ser uma camada e passa a ser um **eixo de pertencimento**, ortogonal às três camadas acima: `Design System` ou `Domain-specific`. Todo componente tem uma camada **e** um pertencimento.

| Exemplo | Camada | Pertencimento |
|---|---|---|
| `Button` | Primitive | Design System |
| `Badge` | Component | Design System |
| `Modal` | Component | Design System |
| `StatusBadge` | Component | Domain-specific (consome `Badge` do DS) |
| `Logo` | Component | Domain-specific (**avaliado e mantido 100% local em 2026-08-20** — não consome `IconTile`; ver §7.2, bloco "Fora do DS", e §14 item 54) |
| `AdminLayout` | Pattern | híbrido — a estrutura (sidebar/header/drawer) é Design System; o conteúdo (rótulos de navegação, rodapé de usuário) é Domain-specific |

Regra objetiva de pertencimento (inalterada da versão anterior): **se o componente importa algo de `src/types` (`Quote`, `Client`, `Product`, `QuoteStatus`...) e/ou contém copy de negócio fixa em português, seu pertencimento é `Domain-specific`.**

- PascalCase, sem prefixo/sufixo de camada (`Button`, não `UiButton`). — OBSERVADO como padrão já em uso (`Logo`, `PageHeader`, `StatusBadge`).

## 6. Tokens de design

### 6.1 Cor e tons semânticos

**DECIDIDO:** o vocabulário oficial de `tone` é `neutral`, `brand`, `info`, `success`, `danger`. **`warning` não é criado agora** — não há, hoje, identidade visual distinta observada para esse estado (alerta e erro compartilham a cor `red` em todo o código atual, ex. `ConfirmModal`).

**DECIDIDO:** `brand` e `info` permanecem semanticamente separados. `blue-*` **não** é substituído indiscriminadamente por `brand-*`. `brand` representa ação/identidade primária; `info` representa informação/estado neutro-informativo.

| `tone` | Mapeamento de cor | Papel | Uso observado |
|---|---|---|---|
| `neutral` | `slate-100`/`slate-600` (bg/texto) | Estado padrão, neutro, "rascunho" | `StatusBadge` (draft) |
| `brand` | `brand-500`/`600`/`700` | Ação primária, identidade de marca | `.btn-primary`, links, ícones de destaque, foco |
| `info` | `blue-50`/`700` (bg/texto) | Informação, "em andamento" | `StatusBadge` (sent), ícones informativos em `IconTile` |
| `success` | `emerald-50`/`500`/`600`/`700` | Sucesso, aprovado, ativo | `StatusBadge` (approved), badge Ativo, botão WhatsApp |
| `danger` | `red-50`/`600`/`700` | Erro, destrutivo, recusado | `StatusBadge` (rejected), `.btn-danger`, `.field-error` |

**OBSERVADO, fora do escopo de `tone`:** `text-blue-100`/`200`/`300` usado como texto secundário sobre fundo escuro (`bg-navy`, sidebar, hero do login) é um uso de `blue` **diferente** de `tone="info"` — é texto-sobre-superfície-escura, não um indicador semântico. Não deve ser confundido com o token `info` acima nem migrado para `brand`.

Demais tokens de cor estrutural (`color.surface`, `color.surface-muted`, `color.border-default`, `color.border-subtle`, `color.text-muted`, `color.accent`) permanecem como definidos em `tokens.md` §4 — sem mudança nesta consolidação.

### 6.2 Tipografia por papel semântico

**DECIDIDO (a partir de decisão explícita):** a tipografia do DS é descrita por **papéis semânticos**, não por uma escala numérica nova e independente. Os valores de cada papel são os já observados no código (ver `tokens.md` §1.8); onde o código usa mais de um valor para o mesmo papel, isso é registrado como variação **OBSERVADA**, não resolvida arbitrariamente aqui.

| Papel | Uso observado (classes reais) | Status |
|---|---|---|
| `display` | `text-5xl leading-[1.1]` (título hero do login) | OBSERVADO — uso único hoje |
| `page-title` | `font-serif text-2xl sm:text-3xl text-navy` (`PageHeader`) | OBSERVADO — consistente nas 6 páginas que usam `PageHeader` |
| `section-title` | Varia: sem classe de tamanho explícita (herda ~body) na maioria dos cabeçalhos de `card`; `text-lg` (resumo financeiro); `text-xl` (título de modal de form); `text-2xl font-serif` (título de modal de detalhe do cliente) | **PENDENTE** — qual valor vira o padrão de `section-title` (ver seção 15) |
| `body` | `text-sm` | OBSERVADO — tamanho dominante da aplicação |
| `body-small` | `text-xs` | OBSERVADO — metadados, labels uppercase |
| `label` | `.label` (`text-sm font-semibold text-slate-700`) | OBSERVADO — já é classe nomeada |
| `caption` | `text-xs text-slate-400` | OBSERVADO — timestamps, texto de apoio esmaecido |
| `eyebrow` | `text-xs font-bold uppercase` + `tracking-[.16em]`/`.18em`/`.2em`/`.22em` (4 valores concorrentes) | OBSERVADO o papel; **PENDENTE** o valor de tracking oficial (ver seção 15) |

`fontWeight.emphasis` (`semibold`, 600) e as famílias `font.heading` (Lora) / `font.body` (Inter) permanecem como já registrado em `tokens.md` §1.9/§4 — sem mudança.

**DECIDIDO (2026-08-19, ao implementar `Input`) — sem prop `icon` em `Input`.** A inspeção dos usos atuais de input-com-ícone (`ClientsPage`, `ProductsPage`, `QuotesPage`, `QuoteFormPage`, `LoginPage`) mostra que o padrão sempre exige um wrapper `relative`, posicionamento absoluto do ícone e padding-left ajustado no campo (`pl-10`/`pl-11`, hoje inconsistentes entre si — ver `tokens.md` §2) — e, no caso da senha do login, o "ícone" é na verdade um botão interativo de alternância, não um elemento decorativo. Isso é responsabilidade de composição, não do primitivo. `Input` permanece o mais próximo possível de `<input>`, sem wrapper próprio; `icon` sai da API prevista. Essa composição pertence a `SearchInput` (busca com lupa/calendário) e `PasswordInput` (toggle mostrar/ocultar) quando forem implementados — nenhum dos dois foi construído nesta tarefa.

**DECIDIDO (2026-08-19, ao implementar `Checkbox`) — `type` não é prop pública.** `CheckboxProps` usa `Omit<React.InputHTMLAttributes<HTMLInputElement>, 'type'>`, removendo `type` da API em nível de tipo (idiomático, sem abstração extra); o componente aplica `type="checkbox"` internamente, depois de `{...props}` no JSX, para que o consumidor não consiga sobrescrevê-lo. Sem props `checked`/`onChange`/`label` customizadas — as nativas já são suficientes para `<Checkbox {...register('campo')} />`.

O consumidor continua responsável pelo padding via `className` (ex. `<Surface className="p-5">`).

**DECIDIDO em 2026-08-20 — auditoria final fecha a pendência `p-5` vs. `p-6` (`tokens.md` §5 item 7): `Surface` não tem, e não deve ter, padding estrutural.**
- **Inventário completo:** 17 ocorrências reais de `.card` em 6 páginas (`ClientsPage`, `ProductsPage`, `QuotesPage`, `DashboardPage`, `QuoteDetailsPage`, `QuoteFormPage`). Busca global por `shadow-card`/`border-slate-200/80` confirmou **zero** estruturas manuais reescrevendo `.card` por fora da classe — todo uso real passa pela classe/componente, nenhum "equivalente escondido" a considerar.
- **`.card` e `Surface.tsx` são byte-idênticos:** `rounded-2xl border border-slate-200/80 bg-white shadow-card`, caractere por caractere, nos dois lugares.
- **10 dos 17 casos têm padding no mesmo elemento que `.card`** (categoria A): `p-5` (4× KPI de `DashboardPage`, mesmo template, + 3× aside de `QuoteDetailsPage` — 7 instâncias/4 padrões de origem), `p-6` (revenue card e conversion card de `DashboardPage`, Observações de `QuoteDetailsPage` — 3 instâncias/padrões), `p-5 sm:p-6` responsivo (3 seções de `QuoteFormPage`). **Nenhum valor chega perto de maioria** — 4/3/3 nos padrões de origem — diferente de decisões anteriores deste DS (ex. ícone `md=18px`, ~35% isolado de 65 usos reais) que tinham evidência muito mais forte antes de virar default.
- **7 dos 17 casos (41%) não têm NENHUM padding no elemento `.card` em si** (categoria B, estruturas compostas): `ClientsPage`/`ProductsPage`/`QuotesPage` (lista: cabeçalho de busca/filtro `p-4 sm:p-5`, corpo = tabela sem padding no card, rodapé = `Pagination` com padding próprio); `DashboardPage` "Orçamentos recentes" (cabeçalho `px-5 py-5 sm:px-6`, corpo = tabela); `QuoteDetailsPage` "Proposta para" (cabeçalho e corpo `p-6`, em `<div>`s separados por `border-b`) e "Itens do orçamento" (cabeçalho `px-6 py-5`, corpo = tabela, rodapé financeiro `p-6` com `border-t` — divisão em 3 regiões, o caso mais claro de "padding não pertence ao card"); `QuoteFormPage` "Resumo financeiro" (cabeçalho escuro `p-5` com `bg-navy` sobrescrevendo o `bg-white` de `.card`, corpo `p-5`). Nesses 7 casos, um padding default no próprio `Surface`/`.card` teria que ser **zerado** pelo consumidor (`p-0` ou equivalente) para não duplicar/conflitar com o padding das regiões internas — um valor default seria ativamente contraproducente, não neutro.
- **Avaliação explícita das 3 estratégias:**
  - **Estratégia A (sem padding)** — a única que não exige nenhum consumidor "brigar" com um default: os 10 casos simples usam `className` livremente (`p-5`, `p-6`, `p-5 sm:p-6`, sem restrição), os 7 casos compostos nunca tocam o padding do `Surface` em si. **Escolhida.**
  - **Estratégia B (default único)** — testada com `p-5` e `p-6`: qualquer um dos dois deixaria 6–7 dos 10 casos "A" precisando sobrescrever via `className` (o mesmo tipo de conflito de utilities já investigado e resolvido empiricamente na migração de `Table`, aqui não re-verificado por já não haver benefício líquido) **e**, mais grave, os 7 casos "B" (41% do total) precisariam de um reset explícito só para não herdar um padding indesejado no elemento errado. Nenhum dos dois valores passa no critério "ausência de conflito de utilities" do item 4.
  - **Estratégia C (prop `padding="sm"|"md"`)** — rejeitada: não há um padrão dominante suficiente (3 valores reais, nenhuma maioria, um deles responsivo) para justificar uma API pública nova; seria, na prática, um `enum` que só espelha `p-5`/`p-6` do Tailwind sem resolver nenhum conflito real — exatamente o que o critério 5 do item 4 pede para evitar.
- **Casos compostos como evidência decisiva:** os 7 casos da categoria B (cabeçalho/corpo/rodapé com paddings diferentes, às vezes assimétricos como `px-6 py-5`, às vezes com `bg-navy` sobrescrevendo `bg-white`) confirmam que padding não é uma responsabilidade estrutural de "ser um cartão" — é uma decisão de composição interna de cada página, variável por região. Isso é consistente com o próprio `.card` legado, que nunca definiu padding em 4+ anos de código.
- **Impacto esperado em migrações futuras:** ao migrar `.card` → `Surface` (fora do escopo desta tarefa), cada consumidor simplesmente move o `className` de padding que já tinha para a mesma posição em `<Surface className="...">` — sem decisão nova a tomar, sem quebra de layout, sem necessidade de "resetar" um default.

**TENTATIVA DE MIGRAÇÃO EM 2026-08-20 — 0 de 17 consumidores migrados; achado estrutural real, `Surface.tsx` não alterado (histórico, resolvido pela decisão abaixo).** Antes de migrar, reconfirmada a equivalência byte-idêntica entre `.card` e `Surface.tsx` (nenhuma divergência nova). Ao auditar o elemento HTML de cada um dos 17 consumidores reais (item obrigatório dessa tarefa, antes não verificado na auditoria do item 46 — que checou só classes, não a tag), constatou-se que **100% deles usam `<section>` (13 casos) ou `<article>` (4 casos, todos em `DashboardPage`) — nenhum usa `<div>`.** Como naquela tarefa `Surface` renderizava exclusivamente `<div>` e a tarefa vedava adicionar `as`/polimorfismo, a migração foi integralmente interrompida (0/17), registrada como pendência (item 20 de §15, ver histórico ali).

**DECIDIDO em 2026-08-20 (tarefa seguinte, dedicada) — `Surface` ganha `as?: 'div' | 'section' | 'article'`, API fechada, resolvendo a pendência acima sem migrar nenhum consumidor.** Não é polimorfismo genérico: avaliada e rejeitada explicitamente a alternativa `as?: React.ElementType`/`as?: T` com suporte arbitrário (`button`, `a`, `nav`, `form`, `main`, `aside`, componentes customizados) — sem evidência real de necessidade; a auditoria dos 17 consumidores encontrou exclusivamente `section`/`article`/(implicitamente) `div`, nada além disso.
- **Tipagem:** união discriminada por `as`, não um único tipo genérico com cast. `SurfaceDivProps` (`as?: 'div'`, `HTMLAttributes<HTMLDivElement>`, `ref?: Ref<HTMLDivElement>`), `SurfaceSectionProps` (`as: 'section'`, `HTMLAttributes<HTMLElement>`, `ref?: Ref<HTMLElement>`), `SurfaceArticleProps` (mesma forma de `Section`, `as: 'article'`) — `SurfaceProps` é a união das três. `section`/`article` usam `HTMLElement` porque o DOM não define uma interface própria para eles (diferente de `HTMLDivElement`); a interface nativa do React (`JSX.IntrinsicElements`) já os tipa assim.
- **Implementação sem `Component` dinâmico nem `as any`:** a função `Surface` narrowing em `props.as` (`if (props.as === 'section') {...}`, `if (props.as === 'article') {...}`, senão `<div>`) — três retornos JSX explícitos, cada um com o elemento literal correspondente. A alternativa óbvia (`const Component = as ?? 'div'; return <Component {...props} />`) foi testada mentalmente e descartada: com `props` de tipo união e um `Component` de tipo dinâmico `'div'|'section'|'article'`, o TypeScript não consegue provar que os atributos espalhados são válidos para o elemento escolhido em tempo de execução, exigindo `as any`/cast amplo — exatamente o que a tarefa pediu para evitar. O narrowing por `if` em `props` (não em variáveis já desestruturadas — desestruturar antes quebra o narrowing de union do TypeScript) resolve isso sem nenhum cast.
- **`ref`:** sem `forwardRef` (padrão React 19 já usado por todo o DS) — `ref` continua prop comum, tipado por ramo (`Ref<HTMLDivElement>` para `div`, `Ref<HTMLElement>` para `section`/`article`), coerente com o tipo real do nó DOM que cada elemento produz.
- **`as` descartado do spread:** cada ramo desestrutura `as` só para excluí-lo de `...rest` (senão vazaria como atributo HTML inválido `as="section"` no DOM); a variável fica sem uso funcional, marcada com `void as;` — idioma padrão para esse caso, não um cast nem uma supressão de erro de tipo (`typecheck`/`lint` confirmam zero erro/warning novo).
- **Classes visuais:** `baseClasses` (`rounded-2xl border border-slate-200/80 bg-white shadow-card`) idênticas nas 3 ramificações — nenhuma prop nova de estilo (`padding`/`variant`/`tone`/`elevation`/`bordered`/`interactive`/`hover`/slots) foi adicionada.
- **Verificação estática contra os 17 consumidores reais (sem migrá-los):** **17/17 representáveis.** Os 13 `<section className="card ...">` (`ClientsPage`, `ProductsPage`, `QuotesPage`; as 6 seções de `QuoteDetailsPage`; as 4 seções de `QuoteFormPage`) seriam `<Surface as="section" className="...">`; os 4 `<article className="card ...">` (todos em `DashboardPage`: KPI, "Orçamentos recentes", revenue, conversion) seriam `<Surface as="article" className="...">`. Nenhum consumidor real ficou de fora — resultado esperado alcançado.
- **`div` como default:** mantido (`as?: 'div'`, ramo padrão) por compatibilidade com a API anterior (nenhum uso existente de `Surface` quebra), mas registrado explicitamente que **nenhum dos 17 consumidores legados usa `<div>`** — `section`/`article` só existem porque a auditoria encontrou evidência real, não por simetria.
- **Validação de tipagem isolada:** como `Surface` ainda não tem consumidor real, a API foi exercitada num arquivo de teste temporário (criado e removido nesta tarefa, não commitado) cobrindo `<Surface>` (default div, com `ref`/`id`/`data-*`/`aria-*`/`onClick`), `<Surface as="section">` e `<Surface as="article">` (mesma cobertura, `ref` do tipo `HTMLElement`), e `<Surface as="button">` marcado com `@ts-expect-error` — o erro esperado realmente ocorreu (confirmado pela ausência do erro "unused `@ts-expect-error` directive"), provando que elementos fora de `div`/`section`/`article` são rejeitados em tempo de compilação. `typecheck` do projeto após remover o arquivo de teste: mesmos 2 erros pré-existentes de `ProductsPage.tsx`, nenhum erro novo. `lint`: mesmo warning pré-existente de `AuthContext.tsx`, zero erros/warnings novos. `vite build` isolado com **hash de CSS e JS idênticos** ao build anterior (`index-CnPnf6uv.css`, `index-Bt0DCaRg.js`, 1900 módulos) — confirma que a mudança de tipagem não gerou nenhum efeito em runtime/CSS (esperado, já que `Surface` ainda não tem consumidor real).
- **Migração dos 17 consumidores continua fora do escopo desta tarefa** — a API agora os representa integralmente (17/17), mas nenhuma página foi alterada; `.card` permanece em uso em `index.css` e nas 6 páginas. Fecha a pendência arquitetural de §15 item 20 (Surface deixa de bloquear a migração); a migração real em si é um novo item de trabalho futuro, não decidido/agendado aqui.

**DECIDIDO (2026-08-19, ao implementar `FormField`) — primeiro componente composto do DS, resumo das decisões:**
- **Sem acoplamento a `react-hook-form`/Zod/tipos de domínio.** `FormField` só conhece `Label`, `FieldError` e um `children` genérico — o uso (`<FormField label="Nome" error={errors.name?.message}><Input {...register('name')} /></FormField>`) continua funcionando sem `Controller`.
- **Estratégia de id, em ordem de prioridade:** (1) prop `id` do `FormField`; (2) `id` já presente no `children`; (3) `React.useId()` — API nativa do React recomendada para este caso exato (gera um id estável e seguro para SSR sem contador global nem id derivado do texto do label).
- **`htmlFor` sai da API prevista** (o inventário original desta tabela previa `htmlFor?`; a implementação usa `id?`, porque quem recebe `htmlFor` é o `Label` interno, não uma prop pública de `FormField` — o consumidor não precisa nomear o atributo do HTML, só opcionalmente fixar o id do campo).
- **`children` tipado como `ReactElement<{ id?, aria-invalid?, aria-describedby? }>`**, não `ReactElement` genérico nem um generic próprio em `FormFieldProps` — preciso o suficiente para o `cloneElement` ser seguro, sem tentar inferir todas as props possíveis de todo campo existente.
- **`React.cloneElement`** é usado para injetar `id` sempre, e `aria-invalid`/`aria-describedby` só quando há `error`. Quando não há erro, essas duas chaves nem são passadas ao clone — o valor original do `children` (se houver) permanece intocado. Quando há erro e o `children` já tinha `aria-describedby`, o valor final é a composição `"{describedby-original} {fieldId}-error"`, nunca uma sobrescrita silenciosa.
- **Sem `role="alert"`, sem `aria-invalid="false"` explícito** quando não há erro — consistente com as decisões já registradas em `FieldError`/`Label`.
- **`Checkbox` não é suportado nesta primeira versão** — seu padrão real de layout (checkbox + rótulo ao lado) é diferente do vertical (rótulo acima → controle → erro) que `FormField` assume. **Confirmado no segundo caso de uso real (`ProductsPage`, 2026-08-19):** o checkbox "Disponível para novos orçamentos" ficou de propósito fora de `FormField`, dentro do mesmo `<label>` legado — a decisão de não suportar `Checkbox` se mantém, não foi revisitada por falta de necessidade real (o layout horizontal continua divergente do vertical).
- **Sem `ref`** — não há evidência de uso que exija encaminhar uma ref para o `<div>` wrapper; não foi adicionado.
- **Layout:** `<div>` sem classes de espaçamento próprias — `Label` já tem `mb-1.5` e `FieldError` já tem `mt-1`; um `gap`/`space-y` no wrapper duplicaria esse espaçamento. Sem card, grid, colunas ou variante de densidade.

**DECIDIDO (2026-08-19, ao implementar `Modal` sobre `@radix-ui/react-dialog`, primeiro componente com dependência headless real):**
- **Auditados os 4 modais reais** (`ConfirmModal`, formulário de `ClientsPage`, formulário de `ProductsPage`, detalhe de cliente em `ClientsPage`) antes de definir a API. Base 100% recorrente: `fixed inset-0 z-50` + `bg-slate-950/40 backdrop-blur-sm` no overlay; `rounded-2xl bg-white p-6 shadow-2xl` no container; botão de fechar `rounded-lg p-2 text-slate-400 hover:bg-slate-100` no canto superior direito.
- **`title` é obrigatório, não `title?`** — revisão em relação ao esboço original da API (seção 15/§7.2). Nos 4 modais reais, todo uso sempre tem um título visível; não há precedente de modal sem nome acessível. Exigir `title` evita, por construção, criar um `Modal` sem `Dialog.Title` — sem precisar inventar um fallback visualmente oculto para um caso que não existe hoje.
- **`maxWidth?: "md" | "2xl" | "3xl"`, default `"2xl"`.** Nomeado pelo próprio sufixo do Tailwind (não por uma escala semântica `sm`/`md`/`lg`/`xl` sem lastro nos dados) — são os únicos 3 valores com precedente real: `max-w-md` (`ConfirmModal`, 1/4), `max-w-2xl` (formulário de `ClientsPage`/`ProductsPage`, 2/4, maioria — vira o default), `max-w-3xl` (detalhe de cliente, 1/4). Nenhum `sm`/`lg`/`xl` — sem uso real.

Aninhar `Content` dentro de `Overlay` (em vez de irmãos, como nos exemplos mais comuns da documentação do Radix) foi verificado diretamente no código-fonte instalado (`@radix-ui/react-dialog@1.1.23`, `@radix-ui/react-dismissable-layer`) antes de implementar, não assumido: (1) o próprio `DialogOverlayImpl` do pacote tem um comentário explícito antecipando os dois casos ("Make sure `Content` is scrollable even when it doesn't live inside `RemoveScroll`, ie. when `Overlay` and `Content` are siblings"), confirmando que aninhar é um padrão previsto; (2) a detecção de "clique fora" do `react-dismissable-layer` usa um listener de captura ligado diretamente ao nó de `Content` (`onPointerDownCapture`), não uma comparação de containment entre `Overlay`/`Content` — um clique no fundo do `Overlay` nunca passa por esse listener, então continua sendo tratado corretamente como "fora" e fecha o diálogo mesmo aninhado. Sem `max-height` explícito na caixa: o scroll acontece no `Overlay` (`overflow-y-auto`), não dentro da caixa — sem header/footer sticky, conforme pedido.

Usar `IconButton` aqui mudaria o visual para aumentar reuso interno, o que a tarefa pediu para não fazer — `Dialog.Close` recebe as classes literais auditadas. - **Sem animação** — os 4 modais atuais não têm; `data-state="open"/"closed"` que o Radix expõe em `Overlay`/`Content` não foi usado para nenhuma classe de transição.
- **Foco delegado ao Radix, sem gerenciamento manual — exceto o retorno de foco, resolvido internamente em 2026-08-19 (ver abaixo).** Focus trap, fechamento por `Esc`, clique fora, portal e ARIA (`role="dialog"`, `aria-labelledby`/`aria-describedby` automáticos via `Dialog.Title`/`Dialog.Description`) vêm de `@radix-ui/react-dialog` sem código adicional. Nenhum `autoFocus`/`querySelector` foi adicionado — o comportamento padrão do Radix (focar o primeiro elemento focável de `Content`, verificado em `@radix-ui/react-focus-scope`) foi observado antes de decidir não intervir nesse ponto específico.
- **RESOLVIDO em 2026-08-19 — retorno de foco sem `Dialog.Trigger`.** A limitação registrada na primeira migração (`Modal` não usa `Dialog.Trigger` — os 4 modais reais abrem a partir de múltiplos botões diferentes, ex. "Novo cliente" + "Editar" por linha em `ClientsPage`, uma relação N-para-1 sem gatilho único; o `onCloseAutoFocus` interno do `Dialog` sempre faz `preventDefault()` e tenta `context.triggerRef.current?.focus()`, um no-op sem `Trigger` que também cancela o fallback do `FocusScope`) foi resolvida **dentro de `Modal.tsx`, sem mudar a API pública**: (1) **captura** — em fase de *render* (não `useEffect`), na transição `closed → open`, `document.activeElement` é lido e guardado num `useRef` só se for `instanceof HTMLElement`; capturar em render (não em efeito) é essencial porque o `useEffect` de auto-foco do `FocusScope` (dentro de `Dialog.Content`, descendente) dispara **antes** do `useEffect` de `Modal` (ancestral) — React roda efeitos de filhos antes dos de pais — então uma captura em `useEffect` capturaria o próprio conteúdo do Modal (o botão de fechar, já focado pelo Radix), não o elemento de origem; capturar em render evita esse problema por completo, pois acontece antes de qualquer commit/efeito. Mutar um `ref` durante o render, sem influenciar o JSX retornado, é seguro (não dispara re-render) e é um padrão documentado do próprio React para "lembrar informação de renders anteriores". (2) **restauração** — só no `onCloseAutoFocus` de `Dialog.Content` (o único fluxo do Radix próprio para isso, disparado igualmente por X/Esc/clique-fora/fechamento programático, já que todos só diferem em como `open` vira `false`, nunca no que acontece depois): se o elemento capturado ainda está `.isConnected` no documento, chama `event.preventDefault()` e `.focus()` nele; caso contrário, não intervém (deixa o no-op padrão do Radix seguir) — nunca força foco em outro lugar. (3) a referência capturada é limpa logo após o uso. Sem `querySelector`, sem IDs de trigger, sem `triggerRef` obrigatório, sem lista de triggers, sem estado global, sem `setTimeout` — só o `useRef`+captura em render+`onCloseAutoFocus` já previstos pela própria arquitetura do Radix para este propósito.

## 8. Estados dos componentes

Modelo por categoria — nenhum estado novo é inventado além do já observado, exceto onde marcado.

### 8.1 Controles interativos (`Button`, `IconButton`, `Input`, `Select`, `Textarea`, `Checkbox`)
- `default`, `hover` (obrigatório em todo controle clicável).
- `focus` — **DECIDIDO (2026-08-19):** `:focus-visible` é o **gatilho** oficial de foco para todo controle interativo do Design System, substituindo `:focus` onde ele é usado hoje (ex.: `.input`) — sem dois gatilhos concorrentes no mesmo elemento. A **aparência visual** do foco (cor, espessura, presença de borda) é decidida **por categoria de componente**, não é obrigatoriamente idêntica em todos:
  - `Button` mantém `ring-2 ring-brand-500 ring-offset-2` (o halo já usado pelo reset global em `index.css:9`) — implementado em `src/design-system/Button.tsx`.
  - `Input`/`Select`/`Textarea` usam `focus-visible:border-brand-500 focus-visible:ring-2 focus-visible:ring-brand-100` — um halo mais leve, sem `ring-offset` — **implementado** em `src/design-system/{Input,Select,Textarea}.tsx`. É a mesma aparência que `.input` já tinha sob `:focus`, só com o gatilho migrado para `:focus-visible`; não há mais `:focus`/`:focus-visible` concorrentes no mesmo elemento.
  - `Checkbox` usa `ring-2 ring-brand-500 ring-offset-2` — **implementado** em `src/design-system/Checkbox.tsx`. Igual à aparência do `Button`, não à de `Input`/`Select`/`Textarea`: diferente de `.input`, o checkbox nunca teve uma segunda regra de foco (`:focus` própria) para reconciliar — só herdava a regra global (`index.css:9`, já `ring-brand-500`+offset), então essa aparência foi só tornada explícita, não escolhida por comparação com outro modelo.
- `active` — hoje não existe em nenhum componente do projeto. Não formalizado como obrigatório nesta especificação.
- `disabled` — `Button`/`.btn`: `pointer-events-none opacity-50`. `Input`/`Select`/`Textarea`/`Checkbox` — **DECIDIDO (2026-08-19):** `disabled:cursor-not-allowed disabled:opacity-50`, reaproveitando o mesmo valor de opacidade já usado por `Button`/`.btn` (sem introduzir uma cor/token novo) — **implementado** nos quatro.
- `loading` (só `Button`) — hoje é só texto (`"Salvando..."`), sem spinner. **PENDENTE** se o DS adiciona spinner visual (seção 15).

### 8.2 Campos de formulário (via `FormField`)
`default`, `focus` (`focus-visible:border-brand-500 focus-visible:ring-2 focus-visible:ring-brand-100`, ver 8.1), `error` (via `FieldError`, renderizada e associada por `aria-describedby` quando `error` é truthy — **implementado**), `disabled` (`disabled:cursor-not-allowed disabled:opacity-50`, ver 8.1). Sem estado de "sucesso"/validado — não há precedente no código. `FormField` (implementado em `src/design-system/FormField.tsx`) associa `Label`/campo/`FieldError` via `htmlFor`/`id`/`aria-invalid`/`aria-describedby`, cobrindo `Input`/`Select`/`Textarea`; `Checkbox` não é suportado nesta primeira versão (ver §7.2).

### 8.3 Feedback semântico (`Badge`, `Progress`, `Toast` via `sonner`)
Tons: `neutral`, `brand`, `info`, `success`, `danger` (seção 6.1). Sem `warning` por decisão explícita.

### 8.4 Contêineres assíncronos (listagens)
`loading` → `Loading`. `empty` → `EmptyState`. `ready` → conteúdo. Um estado `error` de página/listagem formal (distinto do toast pontual) permanece **PENDENTE** (seção 15) — hoje um erro de requisição só dispara `toast.error`, sem estado visual de página.

`open`/`closed` (sem animação de entrada/saída — comportamento observado nos 4 modais atuais; **confirmado em 2026-08-19** ao implementar `Modal`: nenhuma classe/`data-state` de animação foi adicionada, mesmo o Radix expondo `data-state="open"/"closed"` em `Overlay`/`Content`). `busy` — **implementado em `ConfirmDialog`** (2026-08-19), preservado da API legada; nenhum dos 3 consumidores reais passa `busy=true` hoje.

## 9. Acessibilidade

1. **`aria-label` obrigatório em `IconButton`** — já 100% consistente hoje; tipado como obrigatório no DS para não regredir.
2. **`Label` sempre associado via `htmlFor`/`id`** — **implementado**: `FormField` (`src/design-system/FormField.tsx`) gera/resolve o `id` do campo (prop explícita → `id` já presente no `children` → `React.useId()`) e passa `htmlFor={fieldId}` ao `Label` internamente. `Label` isoladamente (`src/design-system/Label.tsx`) continua sem impor a associação por si só — aceita `htmlFor` como prop nativa opcional; a obrigatoriedade é aplicada por quem o compõe (`FormField`).
3. **Diálogos declaram `role="dialog"` e `aria-modal="true"`** — hoje só `ConfirmModal` faz isso; os outros 3 modais inline não. **Implementado em 2026-08-19:** `Modal` (`src/design-system/Modal.tsx`) aplica isso incondicionalmente, via `Dialog.Content` do Radix (`role="dialog"` fixo; `aria-modal` decorre de `Dialog.Root` não receber `modal={false}`).
4. **DECIDIDO E IMPLEMENTADO em 2026-08-19 — arquitetura de acessibilidade do `Dialog`:** usar uma **primitiva headless especializada** em comportamento e acessibilidade de diálogo (focus trap, fechamento por `Esc`, retorno de foco ao elemento que abriu, portal, atributos ARIA) — **sem adotar uma biblioteca completa de componentes visuais**. A biblioteca concreta é **`@radix-ui/react-dialog`** (ver seção 12) — resolve a pendência anterior, que deixava a escolha em aberto até a implementação do `Modal`.
5. **Não remover indicador de foco sem substituto** — o `<select>` transparente de `QuotesPage.tsx:32` (`outline-none` sem novo indicador) não deve se repetir em nenhum componente do DS.
6. **Não usar cor como único indicador de estado** — `Badge`/`StatusBadge` já seguem isso (cor + ícone + texto); manter como regra.
7. **Contraste de texto sobre fundo escuro** não foi auditado quanto a WCAG nesta análise — recomenda-se validação antes de formalizar `text-blue-100/200/300` sobre `bg-navy` como tokens estáveis.
8. **`FieldError` associável via `aria-describedby`/`id`, sem automatismo** — `FieldError` (`src/design-system/FieldError.tsx`) preserva suporte nativo a `id`, sem gerar `id` automaticamente e sem `role="alert"` por padrão (nenhum uso atual da aplicação usa `role="alert"`/`aria-live` nas mensagens de erro). Quem gera o `id` e faz a associação é `FormField` (**implementado**): `errorId = "{fieldId}-error"`, aplicado via `aria-describedby` no campo só quando há `error`, composto com um `aria-describedby` pré-existente no `children` em vez de sobrescrevê-lo. `aria-invalid="true"` só é aplicado quando há erro — nunca `aria-invalid="false"` explícito.

## 12. Stack técnica e dependências

- **Tailwind CSS continua sendo a única infraestrutura de estilo.**
- **`clsx`** (já instalado, hoje sem uso) reativado como utilitário oficial de composição condicional de classes.
- **DECIDIDO — sem wrapper `Icon` sobre `lucide-react`.** Mantêm-se os imports diretos de `lucide-react` em cada componente/página; só a **escala de tamanho** é padronizada (valores numéricos exatos permanecem PENDENTES, seção 15). Isso é uma mudança em relação à especificação anterior, que deixava a existência de um wrapper como pergunta aberta — agora está descartado.
- **`react-hook-form` + `zod` + `@hookform/resolvers` continuam sendo o padrão de formulário.** Todo componente de campo do DS aceita `ref` como prop nativa (React 19, mesmo padrão de `Button`/`Input`/`Select`/`Textarea` — sem `forwardRef`), compatível com `register()`.
- **`sonner` continua sendo o único canal de feedback assíncrono.** Ver seção 7.2/13 — `Toast` é documentado como infraestrutura visual baseada em `sonner`, não como um novo componente próprio do DS a ser implementado do zero.
- **Nenhuma biblioteca de componentes de UI completa é adicionada por padrão** (Radix, Headless UI, Ariakit, MUI, Chakra etc.) — a única exceção arquitetural registrada é a primitiva headless de `Dialog` (seção 9, item 4), que resolve especificamente comportamento/acessibilidade de diálogo, não estilo visual.
- **DECIDIDO E IMPLEMENTADO (2026-08-19) — `@radix-ui/react-dialog@^1.1.23` é a biblioteca headless concreta escolhida para `Dialog`.** Única dependência instalada (`npm install @radix-ui/react-dialog`, 31 pacotes somados às suas próprias dependências transitivas — todas primitivas internas do Radix, como `react-focus-scope`/`react-dismissable-layer`/`react-portal`; nenhum pacote de UI visual). Não instalado: Radix Themes, `@radix-ui/react-alert-dialog` (fica para quando `ConfirmDialog` for implementado, seção 13), nenhuma outra primitiva Radix, nenhum shadcn/ui. Usada exclusivamente como comportamento/acessibilidade (`Dialog.Root`/`Portal`/`Overlay`/`Content`/`Title`/`Description`/`Close`) — todo o visual continua 100% Tailwind, sem Radix Themes nem CSS próprio do pacote (é headless, não emite estilos). Motivo da escolha: é a opção mais madura/testada do espaço "primitiva headless de diálogo apenas" (sem trazer um sistema de design próprio), com controle total de estilo via `className`, modelo controlado (`open`/`onOpenChange`) compatível com o padrão já usado pelos 4 modais atuais, e focus trap/Escape/portal/ARIA prontos sem reimplementação manual.
- **Nenhuma biblioteca de variantes tipadas** (`class-variance-authority`, `tailwind-variants`) é adicionada por padrão — `clsx` cobre o volume atual de variantes.
- **DECIDIDO — sem dark mode nesta etapa.** Nenhuma variante `dark:` é projetada. Tokens de cor continuam como valores fixos do `tailwind.config.ts`, não CSS custom properties. Isso é uma decisão explícita, não uma omissão — se dark mode for necessário no futuro, exigirá revisão da modelagem de tokens.
- **DECIDIDO — sem Storybook/Ladle antes da primeira leva de componentes.** Reavaliar ferramenta de documentação viva/regressão visual **depois** de implementados os componentes fundamentais (seção 14), não antes.
- **Estratégia de testes automatizados do DS** permanece PENDENTE (seção 15) — o projeto não tem nenhum framework de teste configurado hoje.

## 13. Roadmap de implementação

**DECIDIDO — ordem entre `Modal` e `ConfirmDialog`:** `Modal`/`Dialog` é implementado primeiro; `ConfirmDialog` é construído sobre ele. `ConfirmModal` (implementação atual) não é mantido como abstração paralela — quando `ConfirmDialog` existir, `ConfirmModal` é substituído por ele nos três pontos de uso (`ClientsPage`, `ProductsPage`, `QuotesPage`).

**DECIDIDO — ordem entre `Table` e `DataTable`:** primeiro consolidar `Table` (estrutura visual) e migrar as 5 tabelas reais para usá-la; só depois — com base no que essa migração revelar — avaliar se uma abstração `DataTable` orientada a dados (`columns`/`rows`) se justifica. Não implementar `DataTable` de saída.

**Reavaliado em 2026-08-19, após a migração das 5 tabelas reais (ver §14 item 33): `DataTable` continua não justificado no momento.** Nenhuma das 5 tabelas compartilhou definição de colunas, renderização de célula parametrizada, sorting, seleção de linha ou paginação integrada — `Pagination` é sempre um componente à parte, ao lado da tabela, nunca dentro dela. A repetição real observada foi só estrutural (mesma composição `Table`/`TableHeader`/`TableBody`/`TableRow`/`TableHead`/`TableCell`) e visual (largura/padding/hover variando por `className`), exatamente o que os primitives resolvem hoje. Reabrir a avaliação apenas se/quando surgir um caso real com necessidade de sorting/seleção/paginação acoplada aos dados da tabela.

Fases sugeridas (detalhamento da ordem de componentes na seção final desta resposta, não repetido aqui para evitar duplicidade):

1. **Fase 1** — primitivos e componentes de baixo risco/alta maturidade já existente (`Button`, `Input`/`Select`/`Textarea`/`Checkbox`, `Label`, `FieldError`, `Surface`, `PageHeader`, `Loading`, `EmptyState`, `Pagination`).
2. **Fase 2** — componentes de maior duplicação hoje espalhada (`FormField`, `IconTile`, `IconButton`, `Badge`, `SearchInput`, `Table`).
3. **Fase 3** — `Modal` → `ConfirmDialog`; `PasswordInput`; `Progress`.
4. **Fase 4** — reavaliação de `DataTable`, documentação viva (Storybook/Ladle), templates de `Pattern` documentados (não empacotados).

Consumir `IconTile` exigiria sobrescrever via `className` os dois efeitos que `tone` produz (`bg-*`/`text-*`), esvaziando a própria razão de `tone` existir, só para reaproveitar geometria — sem nenhuma duplicação real eliminada. Mesmo critério evidence-based já aplicado a `Surface`/`Button`: só integrar quando há duplicação real a resolver, não por coincidência superficial de valores.
    - **Achado registrado, não elevado a decisão (ver §16):** o mesmo padrão `grid size-10 place-items-center rounded-xl bg-coral` (sem `text-white`/sombra) aparece também no avatar de usuário de `AdminLayout.tsx:25` — uma segunda ocorrência real de "ícone/inicial sobre fundo `coral` sólido", fora do escopo de `Logo` (não é consumidor de `Logo`, é um elemento próprio de `AdminLayout`). Não avaliado nem decidido aqui — mencionado para não se perder, caso uma futura tarefa quisesse investigar um padrão "tile sólido de marca" como um tom adicional (hoje sem justificativa suficiente: apenas 2 ocorrências, uma delas — o próprio `Logo` — com sombra que a outra não tem).
    - `Logo.tsx`/`IconTile.tsx` **não foram alterados**. `typecheck`/`lint`: mesma baseline pré-existente, registrada só para referência (nenhuma mudança de código nesta tarefa).
55. **(2026-08-20, pill Ativo/Inativo de `ProductsPage` migrada para `Badge`)** Última duplicação visual real identificada na auditoria geral anterior. Confirmada a divergência: estado ativo byte-idêntico a `tone="success"`; estado inativo usava `text-slate-500`, um tom mais claro que `text-slate-600` de `tone="neutral"`. **Decisão: aceitar a normalização e migrar** (não a alternativa de manter local) — critério: mesmo papel semântico de `StatusBadge`/`draft` (estado neutro/inativo, já usa `tone="neutral"`/`text-slate-600` em produção sem alteração), direção do impacto visual é mais contraste, não menos, e a divergência é de 1 tom, não uma incompatibilidade estrutural. **Não resolve a pendência global `color.text-secondary`** (`tokens.md` §5 item 6) — decisão específica desta pill, não um precedente automático para outros usos de texto secundário. `Badge.tsx`/`StatusBadge.tsx` **não alterados**; nenhum `tone` novo criado; nenhum `className` usado para tentar reproduzir `slate-500`. Migração: `<Badge tone={item.is_active ? 'success' : 'neutral'}>{item.is_active ? 'Ativo' : 'Inativo'}</Badge>`, sem abstração intermediária. `Badge` passa a ter 2 consumidores reais (`StatusBadge`, `ProductsPage` — o segundo direto, sem wrapper). `tone="brand"` revalidado: continua com zero consumidores reais. `vite build` isolado com **hash de CSS idêntico** ao build anterior — todas as classes (`bg-emerald-50`/`text-emerald-700`/`bg-slate-100`/`text-slate-600`) já existiam no bundle via `StatusBadge`. `typecheck`: mesmos 2 erros pré-existentes de `ProductsPage.tsx`, linha deslocada em +1 pelo novo import; `lint` limpo.

## 16. Observações registradas, não elevadas a decisão nesta consolidação

Achados da revisão crítica que seguem válidos, mas que não fazem parte das 18 decisões recebidas — mantidos aqui para não serem perdidos silenciosamente, sem inflar a lista de decisões pendentes formal:

- `Loading` não tem `role="status"`/`aria-live` — usuários de leitor de tela não são avisados do carregamento.
- ~~`ConfirmModal` (implementação atual) não tem `overflow-y-auto` no wrapper...~~ — **RESOLVIDO.** `Modal` sempre aplica `overflow-y-auto` no overlay (não condicional). `ConfirmModal` foi migrado para `ConfirmDialog` (sobre `Modal`) e **removido** em 2026-08-19 (ver §14 item 37) — a inconsistência não existe mais em nenhum modal real da aplicação.
- `min-h-[calc(100vh-3.5rem)]` do login (`LoginPage.tsx:25`) usa um valor de padding fixo (`3.5rem`) que só corresponde ao padding real a partir do breakpoint `sm` (`sm:p-7`); abaixo disso (`p-4`) a conta fica levemente incorreta.
- Convenção de placeholder `"—"` para valores ausentes e uso de `truncate` para texto longo (nome/e-mail na sidebar, descrição de produto) nunca foram formalizados como convenção de conteúdo.
- Nenhuma tabela usa `scope="col"`/`<caption>`; nenhum campo obrigatório tem indicação visual (`*`) ou `aria-required`.
- `Logo` tem uma prop `compact` na API pública sem nenhum consumidor real que a use (os 3 usos reais são todos `<Logo />` sem props) — auditado em 2026-08-20 (§14 item 54), preservada por instrução explícita da tarefa de não alterar a API.
- O padrão `grid size-10 place-items-center rounded-xl bg-coral` (símbolo do `Logo`, sem `text-white`/sombra) se repete no avatar de usuário de `AdminLayout.tsx:25` — 2 ocorrências reais de "tile sólido `coral`", insuficiente para justificar um tom novo em `IconTile` hoje (auditoria de `Logo`, §14 item 54).
